## 修复：分享冰箱生成二维码失败出现两个 toast（双重 toast 根因）

**现象**：分享冰箱页点「生成分享码」失败时，屏幕上同时弹出两个提示。

**根因**：`utils/cloud.ts` 的 `call()` 封装在云函数返回 `code !== 0` 或网络 `fail` 时，会先弹一个**系统级 `wx.showToast`** 报错；而调用方页面的 `catch` 里又用 TDesign 页内 `Toast` 弹了第二个（如 share-qrcode `生成失败，请重试`），两者叠加 = 两个 toast。

**统一修复**：给 `call()` 增加第 3 个可选参数 `opts: { silent?: boolean }`，当 `silent: true` 时**不**自动弹 toast，改由调用方自己决定提示文案（保留更具体的消息）。把出现双重 toast 的三处失败路径都改为 `silent: true` + 页面自有 toast：
- `pages/share-qrcode/share-qrcode.ts` `onGenerate`：生成失败 '生成失败，请重试'（TDesign Toast）
- `pages/mine/mine.ts` `onThemeChange`：主题切换失败 '切换失败，请重试'（TDesign Toast）
- `pages/fridge-settings/fridge-settings.ts` `onDeleteConfirm`：删除失败 '删除失败'（wx.showToast，上一轮引入的潜在双重 toast，一并修掉）

**排查结论**：其余页面（member-manage / item-detail / item-edit / fridge-create）的 `catch` 均为空 `() => {}`，错误提示靠 `call()` 统一弹出，无重复；成功路径的 Toast 也不受影响（call 成功不弹 toast）。

**经验（可复用）**：本项目约定「云函数错误提示由 `call()` 统一弹」；凡在 `.catch` 里再弹 toast 的调用，必须传 `{ silent: true }`，否则真机会出现双重 toast。

## 修复：新增冰箱后首页"切换冰箱"列表不刷新

**现象**：从「我的」页进入创建冰箱，保存返回后，首页（index）顶部/切换冰箱的列表仍是旧数据，看不到新冰箱。

**根因**：首页与「我的」共用一个**单次消费的共享布尔** `app.globalData.homeDataDirty`。任何数据变更（新增/删除/编辑冰箱、增删物品等）都置 `true`，页面 `onShow` 看到 `true` 就重载并复位成 `false`。问题是：从 mine 创建冰箱返回时，是 mine 的 `onShow` 先消费掉这个标志并复位；等用户切到 index 时标志已是 `false`，index 不再重载 → 列表陈旧。本质是「一个标志被先到的页面抢消费，后到的页面收不到」。

**修复（改成版本号，互不抢）**：
- `typings/index.d.ts` 的 `IAppOption.globalData`：删除 `homeDataDirty`，新增 `fridgesReady`、`fridgeListVersion:number`、`indexSeenVersion:number`、`mineSeenVersion:number`。
- `app.ts` globalData 对应新增（初值 `fridgeListVersion:0`、`indexSeenVersion:-1`、`mineSeenVersion:-1`）。
- 所有原 `app.globalData.homeDataDirty = true` 写入点（scan-result / item-edit / member-manage×3 / item-detail×2 / fridge-settings / fridge-create / fridge 共 11 处）统一改为 `app.globalData.fridgeListVersion++`。
- `index.ts`：`onLoad` 先把 `indexSeenVersion` 对齐当前版本（避免首开重复加载）；`onShow` 改为「版本不一致才 `loadData(false)` 静默刷新」并刷新 `indexSeenVersion`。
- `mine.ts`：`onShow` 改为「版本不一致才 `loadData()`（带骨架），否则沿用全局缓存不闪骨架」；`loadData` 内两处 `homeDataDirty=false` 删除（改由各自 onShow 维护 seen 版本）。

**效果**：冰箱列表数据一变更，版本号 +1；首页与「我的」各自记住「已见版本」，任一方 `onShow` 发现版本变新就刷新，互不影响。首页切换列表、我的冰箱管理列表在新增/删除/编辑冰箱后都会更新。

**经验（可复用）**：微信小程序里「多个页面要各自感知同一份共享数据变更并刷新」时，**不要用单次消费的布尔标志**（先到的页面会抢消费），改用全局版本号 + 每个页面记录自己已见版本，onShow 比对即可。

## 再修：版本号方案真机仍不刷新（首页切换列表还是旧）

**修复（两道保险）**：
1. 解耦 `index.loadData`：拿到 `getFridgeList` 后**立即 `setData({fridges})`**；`getExpiringItems` 改独立 try，失败只清空临期列表、不影响冰箱列表。
2. 新增 `utils/refresh.ts` 的 `refreshFridgeLists()`：遍历 `getCurrentPages()`，对还存活的 `pages/index/index` 与 `pages/mine/mine` 直接调其 `loadData()`（首页传 false 静默、我的传 true 骨架），并把对应 `seen` 版本号同步为当前版本避免返回时 onShow 重复拉。在 `fridge-create` 保存、`fridge-settings` 删除、`scan-result` 加入 三个版本号写入点**之后**调用 → 保存/删除成功瞬间主动刷新，不再依赖 onShow 时序。
3. 三处调用方（`fridge-create.ts`/`fridge-settings.ts`/`scan-result.ts`）`import { refreshFridgeLists }` 并在 `fridgeListVersion++` 后调用。

**经验补充**：列表页 `loadData` 若把"主数据"和"附属数据"绑在同一 try，附属接口失败会连累主数据不提交——**主数据先 setData，附属数据独立请求**。

## 编译报错排查：JSON 的 BOM + wxml 损坏的 </text> 闭合标签

**现象（微信开发者工具）**：
1. app.json 报 SyntaxError: Unexpected token... is not valid JSON -> 根因是文件带 UTF-8 BOM(ï»¿)，WeChat 编译器不认。
2. 多页面 fridge-create.json/item-edit.json 同样报 BOM。
3. 清缓存重编后冒出大量 wxml missing end tag。

**排查结论**：
- 全项目扫到 18 个 JSON 带 BOM（含 2 个页面 json + 16 个云函数 package.json），已全部用 python 字节层 data[3:] 去掉 BOM。
- 2 个 wxml（fridge-create.wxml、item-edit.wxml）带 BOM，已清。
- 真正的 missing end tag 根因：fridge-create.wxml:88、item-edit.wxml:21、item-edit.wxml:43 共 3 处 </text> 的 < 被损坏成 ?，变成 ?/text> -> <text> 开标签找不到闭合，整棵标签树错位级联。用字节级替换 b'?/text>' -> b'</text>' 修复。

**校验手段（可复用）**：
- 查 BOM：open(p,'rb').read(3) == b'ï»¿'。
- wxml 标签平衡：先 re.sub(r'\{\{.*?\}\}', 'XX', content, flags=re.S) 剥掉 {{ }}（里面可能含 > 会骗过正则），再做栈平衡；{{ }} 里的 > 是之前多次误报的元凶。
- 损坏闭合标签扫描：re.compile(rb'\?/([a-zA-Z][\w:-]*)\s*>') 全局搜 ?/tag>。

**经验**：① 小程序里凡 Unexpected token / 非法 JSON，先查 BOM；② 一处 </text> 损坏会让整文件级联报 missing end tag，不要被好多文件吓到，实际就 2 个文件 3 个点；③ 之前编辑期沙箱丢写曾导致文件字节损坏（< -> ?），写文件后务必用 Read/字节校验确认落盘。修复后微信开发者工具重编译即可。
